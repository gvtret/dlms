fix(cosem)!: align Schedule IC 10 method ids with spec (1/2/3 = enable_disable/insert/delete)

IEC 62056-6-2 ED4 (2021) clause 4.5.3 and DLMS UA Blue Book Ed. 12.1
clause 5.1.7 define three specific methods for class_id=10:
  1 = enable_disable
  2 = insert
  3 = delete

CosemScheduleObject previously only recognised two methods and used
the wrong numeric ids:
  1 = insert
  2 = delete
  (no enable_disable surface)

This is a real spec deviation: a client targeting the spec id for
"insert" (2) actually invoked "delete"; a client targeting the spec
id for "enable_disable" (1) invoked "insert"; and a client targeting
the spec id for "delete" (3) silently received MethodNotFound. The
class otherwise matched the spec (attrs 1..2, MaxSupportedVersion=0,
correct UnsupportedFeature semantics for the mutating methods).

Fix:
- Rename kScheduleInsertMethodId to keep the symbol attached to the
  spec id and add kScheduleEnableDisableMethodId (1), kScheduleInsertMethodId
  (2), kScheduleDeleteMethodId (3) at the spec values, with a comment
  citing ED4 4.5.3 / Blue Book 5.1.7.
- Extend InvokeMethod to accept all three spec ids and return
  UnsupportedFeature for each (the built-in object does not own
  schedule-entry mutation policy, matching IC 9 / IC 11 / IC 22 style).
- Update the CosemScheduleObject.MethodsReturnUnsupportedFeature
  regression test: ids {1, 2, 3} -> UnsupportedFeature, ids
  {0, 4, 5} -> MethodNotFound.

Breaking change: callers that hardcoded the previous (non-spec) ids
1=insert / 2=delete must update to 2=insert / 3=delete. Callers that
were already passing spec ids are unaffected (they now reach the
correct branch).

Updated docs/ic_support_matrix.md and lib/dlms-cosem/docs/01_cosem_api.md
to list the three spec ids. Bumped VERSION to 0.73.0 and added the
corresponding CHANGELOG entry. Verified with the full COSEM gtest
binary (275/275 passing) and full ctest suite (936/936 passing).

BREAKING CHANGE: CosemScheduleObject method ids now follow IEC 62056-6-2
ED4 (2021) 4.5.3: 1=enable_disable, 2=insert, 3=delete. Previously the
implementation exposed 1=insert, 2=delete with no enable_disable surface.
