fix(cosem): gate M-Bus Client IC 72 attrs 13/14 to version >= 1

IEC 62056-6-2 ED4 (2021) clause 4.8.3 (class_id=72, version=1) adds
attributes 13 (configuration, long-unsigned) and 14
(encryption_key_status, enum) on top of the v0 attribute table from
DLMS UA Blue Book Ed. 12.1 clause 5.7.1, which stops at attribute
12. The CosemMBusClientObject implementation previously registered
both attribute ids unconditionally and treated them as freely
readable/writable on v0 instances, which is a spec deviation:
clients targeting a v0 server must see AttributeNotFound for ids 13
and 14, not their backing buffers.

Gate attrs 13 and 14 in three places: the CosemAccessRights
initialisation in the unified constructor (the SetAttributeAccess
calls are only emitted when descriptor_.key.version >= 1u so v0
instances report NoAccess), the ReadAttribute switch (return
AttributeNotFound and clear the output when version < 1u), and the
WriteAttribute switch (return AttributeNotFound when version < 1u,
before the writable-access check). The constructor signatures,
MaxSupportedVersion = 1u, default-version behaviour and the method
set (ids 1..8 returning UnsupportedFeature) are unchanged; callers
that supply v1 (the default) see no behavioural difference.

Added the regression test
CosemMBusClientObject.Version0DoesNotExposeConfigurationOrEncryptionKeyStatus
which constructs an object with explicit version 0 and asserts that
(a) AccessRights().AttributeAccess(13/14) is NoAccess,
(b) ReadAttribute(13/14) returns AttributeNotFound and clears the
    output buffer,
(c) WriteAttribute(13/14) returns AttributeNotFound, and
(d) attributes 1..12 remain readable.

Updated docs/ic_support_matrix.md and lib/dlms-cosem/docs/01_cosem_api.md
to record the v0-vs-v1 attribute table difference. Bumped VERSION to
0.72.0 and added the corresponding CHANGELOG entry. Verified with
the full COSEM gtest binary (275/275 passing) and full ctest suite
(936/936 passing).
